エージェントが作ったファイルは全て新規で、メンテナの作業と重ならない（.github/workflows/test.yml のみ既存ファイルへの追記）。

W-3. docs ジョブの README 検査

合意時点の状況: 追加した docs ジョブは fail していた。README.html がメンテナの .md 変更に対して古かったためである（生成し直すと差分が出ることを確認済み。この時点ではファイルを触っていない）。これは D-12 で「README.html の鮮度検査も同じジョブに乗せる」に合意した結果、意図どおり検出されたものだった。その後この節の推奨どおり W-1 の後に再生成を同梱したので、この fail は解消している（§1 の W-3 を参照）。

選択肢 利点 欠点
README を再生成して同梱 ジョブが通る。生成物が最新になる 生成物はメンテナの .md 変更に依存するので、エージェントが再生成するとメンテナの作業の一部をエージェントが作ったことになる。W-1 と同じ問題
README 検査を外す 今すぐ通る。alignment 文書だけ検査する D-12 で得た「ついでに README も検査できる」という利点を捨てる。README.html が古いまま気づけない状態に戻る
continue-on-error にする 落ちても止まらない 検査が事実上無効になる。赤いまま放置される典型
そのまま fail させておく 何も曲げない。W-1 が解決すれば自然に直る それまで CI が赤い

エージェントの推奨: README を再生成して同梱、ただし W-1 でメンテナがコミットした後にエージェントがやる。 順序を守れば W-1 の問題は起きない。W-1 が「メンテナがコミットする」なら、その直後にエージェントが再生成して W-2 の CI コミットに含める。

W-4. samepage のファイル権限

合意時点の状況: --finalize で新規パスに出力すると、ファイルが 0600 で作られていた。_write_atomic が mkstemp（常に 0600）で作ったあと、copymode を既存ファイルにしか適用しないためである。0001-grill-on-samepage.final.html もこのとき 0600 で生成され、手で chmod 644 した。その後 W-4 の決定で cli.py を修正したので、現在の出力は umask に従う（§1 の W-4 を参照）。

選択肢 利点 欠点
cli.py を直す .final.html は SKILL.md §8 で「配布・公開する側」と定義されている成果物なので、0600 はその用途を壊している。修正は数行。cli.py はメンテナが変更中のファイルに含まれないので衝突しない 0001 の合意範囲外の変更。samepage 本体に触ることになる
issue として残す 範囲を守れる。優先度を別途判断できる 直るまで finalize のたびに手で chmod が要る
何もしない 追加作業ゼロ 同上。かつ忘れる

エージェントの推奨: cli.py を直す。 範囲外ではあるが、finalize の出力は「配布するもの」と明記されている以上、既定で他者が読めないのは仕様と実装の食い違いである。ただしこれはエージェントの判断ではなくメンテナの判断なので、範囲を守るほうを選ぶなら issue に落とす、と添えた。
