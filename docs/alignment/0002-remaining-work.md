# 残作業の進め方

ALIGNMENT 0001 で合意した実装計画のうち、step 1 と step 6 が未着手のまま残っている。その解除方法と、成果物の扱いを決める。

## 0. この文書について

これは ALIGNMENT 0001（grill-on-samepage の設計）の**実装フェーズで発生した作業判断**を扱う 2 つ目のセッション。設計そのものは 0001 で合意済みで、ここで蒸し返さない。

この文書は `docs/build_alignment_html.py` で生成されている。0001 は手書き HTML だったので、**これがビルダーの実地検証を兼ねる**。

## design tree

- [W-1] 未コミット作業の扱い :: 確定 :: AI が develop でコミット
  - [W-3] docs ジョブの README 検査 :: 確定 :: 後で AI が再生成
- [W-2] 新規成果物のコミット :: 確定 :: 段階ごとに分ける
- [W-4] samepage のファイル権限 :: 確定 :: cli.py を直す
- [W-5] CLAUDE.md の更新 :: frontier
- [W-6] develop への統合 :: frontier

## 3. 今回のラウンド

実装が終わったことで 2 つ問える状態になった。どちらも上流の決定が片付くまで問えなかったもの。

### W-5. CLAUDE.md の更新

`CLAUDE.md` は AI 向けのリポジトリ運用ルールで、今回の変更で 2 箇所が実態と合わなくなった。

- 「`data-sp-*` / `sp-` プレフィックス、JSON フィールド名は `docs/design.md` と `SKILL.md` が正」 — **`SKILL.md` はルートから移動した**（`skills/samepage/SKILL.md`）。パスが古い。
- ALIGNMENT 文書が SSOT になったが、`CLAUDE.md` はその存在を知らない。次のセッションの AI は `docs/alignment/INDEX.md` を読まずに作業を始めることになる。

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **パス修正 + SSOT の条項を追加** | 次のセッションが SSOT から始められる。D-1 で「合意が文書として残る」を選んだ意味が、AI の側からも効くようになる | `CLAUDE.md` が長くなる。ALIGNMENT を読む手間が毎セッション増える |
| **パス修正だけ** | 最小の変更。壊れている記述だけ直す | 索引があっても誰も見ない状態が続く。D-6 と D-11 で索引を作った意味が薄れる |
| **触らない** | 変更ゼロ | `SKILL.md` のパスが間違ったまま残る |

**推奨: パス修正 + SSOT の条項を追加。** 「設計上の判断に迷ったら `docs/alignment/INDEX.md` を見る。そこで確定している決定を勝手に覆さない」の 2 行で足ります。索引を作ったのに誰も参照しないのが一番もったいない。

### W-6. develop への統合

`feature/grill-on-samepage` に 8 コミットある。`develop` には Copy JSON の 1 コミットだけ。

`CLAUDE.md` は「`main` へのマージ・直接コミット・push は AI は行わない」と定めていますが、`develop` への統合については明示がありません。最後の一文「PR 作成やマージは提案までに留める」を広く読むなら、`develop` へのマージも私はやらないほうがよい、と読めます。**この解釈はあなたが決めることなので、聞きます。**

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **AI が develop にマージする** | 一手で終わる。feature は同じコミットを指すので早送りになる | `CLAUDE.md` の「マージは提案までに留める」の広い読みに反しうる |
| **PR を作るところまで（マージはしない）** | `CLAUDE.md` の文言に素直。差分をレビューしてから統合できる | `gh` で PR を作ると push が発生する。push も AI がやらない範囲なら、これも外れる |
| **feature のまま置く** | 何も起きない。あなたが好きなときに統合できる | 8 コミットが手つかずで残る |

**推奨: feature のまま置く。** `CLAUDE.md` の趣旨は「統合の判断はメンテナが持つ」だと読めるので、私からは動かさないのが安全です。マージしてよいなら明示してください。

## 4. 判断の記録（合意時点の材料）

### W-1. 未コミット作業の扱い

step 1 と 6 のブロックを解除する方法。

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **あなたがコミットする** | 最も安全。作業の帰属が正しく、あなたのコミットメッセージで履歴に残る。私は差分の意図を推測しなくてよい | 私が待つことになる |
| **私がコミットする** | 一手で先に進む | **他人の作業を AI がコミットすることになる。** `samepage.js` の 47 行の変更、`test_browser.py` の変更、デモ画像の再生成の意図を私は把握していない。要約を書けない |
| **stash して進める** | ファイルを触らずに step 1/6 を進められる | stash は事故のもと。`SKILL.md` の移動と README の書き換えが絡むので、復元時に衝突しうる。あなたの作業が一時的に消える |
| **step 1/6 を当面やらない** | 何も壊さない。今ある成果物だけで止める | D-3 が未実施のまま。`${CLAUDE_PLUGIN_ROOT}` を前提に書いた `skills/grill-on-samepage/SKILL.md` が動かないので、**作った grill スキルを実際に試せない** |

**推奨: あなたがコミットする。** 他人の変更を要約なしにコミットするのは避けたい、というのが理由です。`samepage.js` の 47 行が何を意図した変更なのかは、あなたにしか書けません。

### W-2. 新規成果物のコミット

私が作ったファイルは全て新規で、あなたの作業と重なりません（`.github/workflows/test.yml` のみ既存ファイルへの追記）。

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **段階ごとに分ける** | 0001 の実装計画の段階と 1:1 で対応し、あとから「どの決定がどのコミットになったか」を追える。revert の単位が小さい | コミットが 4〜5 個になる |
| **1 コミットにまとめる** | 履歴が簡潔。機能として不可分ではある | どの決定の実装かが本文でしか分からない |
| **コミットしない** | あなたが内容を見てから判断できる | 作業ツリーが膨らみ続ける |

**推奨: 段階ごとに分ける。** ビルダー / スキル定義 / テスト / CI / 合意文書、の 5 つ。各コミットメッセージに根拠となる決定 ID（D-5、D-13 など）を書けば、SSOT とコードが相互参照できます。

### W-3. docs ジョブの README 検査

追加した `docs` ジョブは**現状 fail します**。`README.html` があなたの `.md` 変更に対して古いためです（生成し直すと差分が出ることを確認済み。ファイルは触っていません）。これは D-12 で「README.html の鮮度検査も同じジョブに乗せる」に合意した結果、意図どおり検出されているものです。

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **README を再生成して同梱** | ジョブが通る。生成物が最新になる | 生成物はあなたの `.md` 変更に依存するので、**私が再生成するとあなたの作業の一部を私が作ったことになる**。W-1 と同じ問題 |
| **README 検査を外す** | 今すぐ通る。alignment 文書だけ検査する | D-12 で得た「ついでに README も検査できる」という利点を捨てる。README.html が古いまま気づけない状態に戻る |
| **`continue-on-error` にする** | 落ちても止まらない | 検査が事実上無効になる。赤いまま放置される典型 |
| **そのまま fail させておく** | 何も曲げない。W-1 が解決すれば自然に直る | それまで CI が赤い |

**推奨: README を再生成して同梱、ただし W-1 であなたがコミットした後に私がやる。** 順序を守れば W-1 の問題は起きません。W-1 が「あなたがコミットする」なら、その直後に私が再生成して W-2 の CI コミットに含めます。

### W-4. samepage のファイル権限

`--finalize` で新規パスに出力すると、ファイルが `0600` で作られます。`_write_atomic` が `mkstemp`（常に 0600）で作ったあと、`copymode` を**既存ファイルにしか適用しない**ためです。今回の `0001-grill-on-samepage.final.html` も 0600 で生成され、手で `chmod 644` しました。

| 選択肢 | 利点 | 欠点 |
|---|---|---|
| **`cli.py` を直す** | `.final.html` は SKILL.md §8 で「配布・公開する側」と定義されている成果物なので、**0600 はその用途を壊している**。修正は数行。`cli.py` はあなたが変更中のファイルに含まれないので衝突しない | 0001 の合意範囲外の変更。samepage 本体に触ることになる |
| **issue として残す** | 範囲を守れる。優先度を別途判断できる | 直るまで finalize のたびに手で chmod が要る |
| **何もしない** | 追加作業ゼロ | 同上。かつ忘れる |

**推奨: `cli.py` を直す。** 範囲外ではありますが、finalize の出力は「配布するもの」と明記されている以上、既定で他者が読めないのは仕様と実装の食い違いです。ただしこれは私の判断ではなくあなたの判断なので、範囲を守るほうを選ぶなら issue に落とします。
